   No "sbcam669 ON" line exists. After the respring at 18:37:28 (pid 14350)
   every 2 s: "camera658 com.beeper.chat.ios wants the camera but the display
   layout publisher is not known yet". The publisher was only learnt from
   SpringBoard's own -[FBSDisplayLayoutPublisher addElement:] calls; after a
   respring the stage's hooks go in after the home screen, SpringBoard had

   arbiter start, on the first staged card, and retried 0.5/1/2/3/5 s then
   every 5 s until found. Accepts any object answering addElement: (the 669
   code also required class FBSDisplayLayoutPublisher). Nothing is created (a
   second main-display publisher would publish over SpringBoard's layout).
   Log: "presence670 display layout publisher acquired via <route> (<class>)"

3) Why Messenger works
   Messenger's camera is an in-process UI (its own views, its own
   AVCaptureSession). On a card the app gets the card as its window and
   screen size, and Messenger's camera lays itself out for that size: preview
   aspect-filled to the window, top buttons pinned to the top edge, capture
   row pinned to the bottom. The stage has nothing to fix. If DynamicStage's
   in-app camera layout (layout664/667: phone size + width fill, bottom-aligned)
   had engaged in Messenger, its top would be cropped exactly like Messages in
   668 - the user sees every button, so it evidently lays out at card size.
   No Messenger line has reached any uploaded log (relay667 watches its tmp
   file but nothing came through; Messenger was not put on a card in those
   logs), so this is inferred, not logged.
   Messages' camera is different: it is Apple's camera EXTENSION
   (CameraMessagesApp), another process shown through a remote view. It lays
   out phone-shaped (4.5.666 log: card-sized view -> close X at top worked,
   shutter row below the card). A ~430x932 (0.46 aspect) layout cannot fill a
   420x458 (0.92 aspect) card without cropping ~half or letterboxing ~half.
